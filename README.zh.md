# open-system-one

**对 TypeSafe [Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev) 的独立可复现基准测试，对手是纯 CPU 的开源方案。**

这**不是** Jev 的开源实现，也不声称超过了它。
这是一次测量：10,000 个分类/路由决策，同一台机器，同一份选项描述，
跑过六种不同的技术栈——以及一份诚实的记录：哪些想法有用、哪些没用、
每一种在延迟、内存、CPU 上各要付多少钱。

**完整叙述** — [含八个失败尝试的全文](https://huggingface.co/blog/dylantom2012/i-benchmarked-jev-against-open-cpu-only-stacks-it)

## Jev 是什么，以及我们要验证的假设

Jev 是所谓 "System One Model"：它不生成文本。你提交一段 `state` 和一组带类型的问题，
问题的选项（`criteria`）**在请求时才给**，它返回一个选择加上校准过的概率。
TypeSafe 宣称在分类任务上比前沿 LLM 快 40–200 倍、便宜 40–400 倍。

社区的第一反应——也是我们的——是：

> Jev ≈ 一个快速文本编码器 + 一个极小的决策头。

API 的形状支持这个猜测：既然 `criteria` 是逐请求给的，Jev 就不可能是固定输出维度的
分类头，它只能对 *(state, 选项)* 这样的配对打分再排序。

于是我们用开源零件照着搭了一个，然后量差距。

## 基准设计

10,000 个任务，四个公开数据集各 2,500 条。选它们是为了**覆盖难度谱**，
而不是为了让某个方法好看：

| 数据集 | 选项数 | 考什么 |
|---|---|---|
| SST-2 | 2 | 情感——词汇线索极强 |
| AG News | 4 | 主题——类目名抽象且极简 |
| Emotion | 6 | 细粒度情绪——标签名本身几乎不带语义 |
| BANKING77 | 77 | 意图路由——大量互相混淆的选项 |

切分由固定种子确定性重建（`data.py`），逐条可复现。
**不重新分发任何数据集正文**，见 [DATA_LICENSES.md](DATA_LICENSES.md)。

所有本地数字：**Apple M5 Pro，纯 CPU，batch = 1**，每个模型在独立进程里测量。
Jev 通过 Cloudflare Workers AI（`typesafe/jev`）调用。

## 结果

每条链路都跑了两遍：一遍用**裸标签名**当选项（`card_arrival`、`Sci/Tech`），
一遍用**一句话的丰富描述**（[`descriptions.py`](descriptions.py)）——
**同一份描述，一字不差地给所有方案**。两种条件都报，因为两种都不中性（见下）。

| 方案 | sst2 (2) | ag_news (4) | emotion (6) | banking77 (77) | 宏平均 |
|---|---|---|---|---|---|
| typesafe/jev — 裸标签名 | 89.8 % | 88.3 % | 58.6 % | 78.4 % | **78.8 %** |
| typesafe/jev — 丰富描述 | 91.6 % | 88.6 % | 59.0 % | 77.8 % | **79.3 %** |
| 交叉编码 base — 裸标签名 | 85.5 % | 84.4 % | 76.2 % | 68.8 % | **78.7 %** |
| 交叉编码 base — 丰富描述 | 84.5 % | 84.6 % | 71.7 % | 56.9 % | **74.4 %** |
| 双塔 + Fly — 裸标签名 | 81.1 % | 66.3 % | 43.6 % | 63.2 % | **63.6 %** |
| 双塔 + Fly — 丰富描述 | 82.8 % | 80.0 % | 50.8 % | 65.8 % | **69.9 %** |

**各方案的最好成绩，零样本，双方都没有标注：**

| | 最佳宏平均 | 最佳条件 | p50 延迟 | 内存 |
|---|---|---|---|---|
| `typesafe/jev`（云端） | **79.3 %** | 丰富描述 | 381 ms † | 云端 |
| 交叉编码器 ModernBERT-base-zeroshot (149M) | **78.7 %** | 裸标签名 | 50–616 ms * | — |
| 双塔 + 8 个浮点数的头 | 69.9 % | 丰富描述 | 15.7 ms | 490 MB |
| Qwen2.5-0.5B 生成式 | 49.6 % | 裸标签名 | 112 ms | 2382 MB |

**一个 149M 的开源模型，跑在 CPU 上，落后 Jev 0.6 个百分点。**

\* 随选项数线性增长：2 个选项 50 ms，77 个选项（裁剪到 20）616 ms。
† 以网络往返为主，见「局限」。

### 不存在对所有架构中性的选项描述

这是我们学到的最有用的一件事。同一个改动——把简短标签换成一句话描述——
让三种架构朝**不同方向**移动：

| 对丰富描述的反应 | sst2 | ag_news | emotion | banking77 | 均值 |
|---|---|---|---|---|---|
| `typesafe/jev` | +1.8 | +0.4 | +0.4 | −0.5 | **+0.5** |
| 双塔（余弦相似度） | +1.7 | **+13.7** | +7.2 | +2.5 | **+6.3** |
| 交叉编码器（NLI） | −1.0 | +0.2 | −4.5 | **−11.9** | **−4.3** |

- **余弦相似度没有能力扩展标签的语义。** `World / Sports / Business / Sci-Tech`
  对点积来说几乎零信号，所以把类目写成句子之后，双塔在 AG News 上直接涨 13.7 pp。
- **交叉编码器和 Jev 内部已经做了这件事**，所以毫无收益——而且交叉编码器
  还被长假设句干扰。
- **BANKING77 暴跌 11.9 pp 是我们自己造成的，也最有启发**：77 条描述里有 70 多条
  以 *"The customer …"* 开头。这个共享前缀让所有选项作为 NLI 假设句时几乎一模一样。
  2 个选项时共享前缀无害，77 个选项时是灾难。

所以"给所有系统同样的文本"**不等于**公平。**verbaliser 的写法本身就是一个
依架构而异的调参旋钮**，我们把 `descriptions.py` 一并发出来，就是为了让人能写出
更好的版本并重跑。

### 给 2,000 条标注——**不能和 Jev 相比**

Jev 一条标注都拿不到，所以这是另一个问题，不是胜利。

| 方案 | 宏平均准确率 | p50 延迟 | 内存 |
|---|---|---|---|
| ModernBERT-embed + 线性头 | **82.6 %** | 15.8 ms | 490 MB |
| MiniLM-L6 + 线性头 | 79.5 % | 2.8 ms | 452 MB |
| **potion-base-8M（静态嵌入）+ 线性头** | **78.2 %** | **0.1 ms** | **82 MB** |

分任务看，ModernBERT-embed + 头 对 Jev：**BANKING77 88.8 % vs 77.8 %（+11.0）**、
AG News +0.9、Emotion +7.2、SST-2 −5.8。

最后一行是我们认为最有意思的结果：一个 8M 参数的静态嵌入
（纯查表——前向过程里没有 attention、没有矩阵乘法），加上一个**全部参数是 8 个浮点数**
的决策头，达到了云端决策模型的准确率，延迟 0.1 ms、内存 82 MB。这个头训练耗时 0.1 秒。

## 更新 —— Laya，以及第四种架构

Jev 发布一周后，[Laya](https://huggingface.co/convaiinnovations/laya) 出现了：Apache-2.0
的 System One 模型，ModernBERT-large + 决策头，421M 参数。它**一次前向回答所有选项**——
每个选项在自己的 `[MASK]` 位置打分。这正是我们的交叉编码器做不到的事，也是我们延迟随
选项数增长的根因。

我们用同一批 10,000 条、同样的裸标签、同一套测量纪律跑了它。
**据我们所知，这是第一次把 Laya 和 Jev 放在完全相同的样本上测量。**
（Laya 自己的 README 引用的是第三方发布的 Jev 数字，样本不同、72 vs 77 标签；
我们这一列是直接实测的。）

| 方案 | sst2 | ag_news | emotion | banking77 | 宏平均 | p50 延迟 |
|---|---|---|---|---|---|---|
| `typesafe/jev`（丰富描述） | 91.6 % | 88.6 % | 59.0 % | 77.8 % | **79.3 %** | 381 ms |
| 交叉编码 149M（裸标签） | 85.5 % | 84.4 % | **76.2 %** | 68.8 % | **78.7 %** | 50–616 ms |
| **Laya 421M（裸标签）** | 86.5 % | **93.9 %** | 58.2 % | 54.3 % | **73.2 %** | 19–86 ms *(MPS)* / **60–309 ms** *(CPU)* |
| 双塔 + 决策头，2000 标注 | 85.8 % | 89.5 % | 66.2 % | **88.8 %** | **82.6 %** | 15.8 ms |

三个结论：

**Laya 在 AG News 上完胜**——93.9%，比 Jev 高 5.3 pp。
它 README 自称 0.950，我们实测 0.939；它发布的 Emotion 是 0.595，我们实测 0.582。
**它的自报数据经得起核对**，这一点值得明说。

**它的高基数弱点是真的，而且我们部分修好了。** Laya 的文档诚实地解释了失败原因：
77 个选项共享固定的 `head_max_len`，每个标签只分到 3–4 token，文本不再可区分。
它建议*"把大选项集拆成两步、由粗到细的层次化选择"*——**但没有实现**。
我们为自己的交叉编码器独立做过这个东西，于是直接装了上去：

| BANKING77，77 选项 | 准确率 | p50 |
|---|---|---|
| Laya，全部 77 选项 | 54.3 % | 86.3 ms（MPS）/ 309.0 ms（CPU） |
| **Laya + 我们的零样本双塔裁剪到 top-20** | **60.8 %** | **39.8 ms（MPS）/ 169.9 ms（CPU）** |
| *（裁剪天花板，recall@20）* | *97.8 %* | — |

**+6.5 pp，延迟还砍了一半。** 距离 Jev 在该任务上仍差 17 pp，所以 token 预算问题是
被缓解而不是被解决——但这个补丁只要一次廉价的双塔前向，而且是今天所有尝试里
**唯一一个准确率和延迟同时变好的组合**。

**更正 —— Laya 原来那组延迟是 Apple GPU，不是 CPU。** 我们最初把它当成 CPU 数字发出去了，
这是错的。`laya.load()` 会自动按 `cuda > mps > cpu` 选设备，在这台 Mac 上它悄悄选了 **mps**，
而本仓库其他所有链路都是纯 CPU、batch=1。按同一口径重测，Laya 在 CPU 上是
59.5 ms（sst2）/ 78.0 ms（ag_news）/ 61.9 ms（emotion）/ **309.0 ms**（banking77），
约为 MPS 的 3 倍。这基本抹掉了它在最难那个任务上相对 Jev 的延迟优势（309 ms vs 381 ms），
而准确率仍然是 54.3 % 对 77.8 %。反过来，这让裁剪更值钱而不是更不值钱：CPU 上它把 309 ms 压到 170 ms。

教训不止于这一个数字 —— 我们对**内存**有严格纪律（一个模型一个进程），却对**设备**完全没有。
凡是"自动选择"的东西（device、dtype、线程数、batch）都必须写进结果文件，而不是靠运行时记忆。
`laya_bench.py` 和 `laya_shortlist.py` 现在都会记录 `device`，并支持 `LAYA_DEVICE` 覆盖。

**三种架构以三种方式失败。** 双塔：文本和选项从不交互，抽象标签直接杀死它。
交叉编码：每个选项一次前向，延迟随基数增长。单次前向 option marker：
所有选项共享一个 token 预算，基数摧毁的是准确率而不是速度。
没有免费午餐，只能挑一个你受得了的失效模式。

## 更新 —— 决策头的目标函数一直是错的

Laya 用 RLCD 针对严格恰当评分规则训练。这促使我们回头看自己的目标函数：
`0.7 × 均值准确率 + 0.3 × 最差任务准确率`——**它对"诚实报告概率"零奖励**。
我们把它换成对数分，温度在每次评估里就地最优化。

| ES 目标 | 宏平均准确率 | 平均 ECE | 平均 NLL |
|---|---|---|---|
| 准确率（原） | 82.6 % | 0.018 | 0.490 |
| **严格恰当（对数分）** | **83.6 %** | 0.018 | **0.462** |

结果和预期相反。**校准没有变化**（两边都是 ECE 0.018）——在独立 dev 集上做温度标定
这一步早就把校准做了，目标函数里缺校准项其实没有造成损害。真正改善的是**准确率**，
+1.0 pp，SST-2（+1.8）和 Emotion（+2.0）最明显。

原因关乎优化而非校准：准确率是阶跃函数，(1+λ)-ES 面对的是一片平台；
对数分连续、且奖励"分对得有多稳"，这给了进化策略某种类似梯度的东西。
**我们本来是去找更好的概率，结果找到的是更好的搜索信号。**

## 更新 —— 中文，以及一个置信度陷阱

Laya 有一个多语种 checkpoint（mmBERT-base，322M，100+ 语言）。它自己的基准覆盖
MASSIVE 和 XNLI；我们测了它没测的：**CLUE/TNEWS** 中文新闻标题分类，15 类，600 条。

| checkpoint | 准确率 | 平均置信度 | 过度自信差距 | p50 |
|---|---|---|---|---|
| `laya-multilingual` | **39.2 %** | 0.756 | +0.365 | 14.3 ms |
| `laya`（英文根） | 22.5 % | **0.968** | **+0.743** | 42.5 ms |
| *随机* | *6.7 %* | — | — | — |

英文 checkpoint 跑中文是危险的那一种：**只有 22.5% 正确，却 96.8% 自信。**
这在中文上复现了 Laya 自己记录的高棉语失效模式——*"模型在错的时候依然自信，
所以置信度门控救不了你"*。如果你服务多语种流量，**在前向之前按文字系统路由，
不要指望置信度阈值能拦住它**。

多语种 checkpoint 是可用的——6 倍于随机、14 ms——但它**同样过度自信 0.365**。
在信任它给出的任何概率之前，先在你自己的数据上标定温度。

## 哪些没用

八个我们试过、否则多半会想当然认为有效的想法。它们花了我们一天；
这大概是本仓库里最可能帮你省下一天的部分。

| 想法 | 结果 |
|---|---|
| 模板集成（3 个 NLI 假设句），base 骨干 | **0.0 pp** —— 三个模板犯的错高度相关 |
| 进化策略搜决策头权重，诚实的 LODO 迁移 | **−1.5 pp** —— 负迁移；只在底层信号很差时才有用 |
| 交叉编码器放大 149M → 395M | 三个任务 **+2.8 / −3.2 / +0.2 pp** —— 3 倍算力换来净零 |
| 用 Qwen2.5-1.5B 对 top-5 做列表式精排 | 比交叉编码器单独用**低 1.0 pp** |
| 对 NLI 分数做列中心化 | 宏平均 **0.0 pp** —— BANKING77 +2.6，Emotion −3.1，互相抵消 |
| 非对称前缀 `search_query:` / `search_document:` | **−1.8 pp** —— 靠相似度分类不是检索 |
| 把交叉编码器蒸馏进双塔打分头 | 比老师**低 5.4 pp**，Emotion 上直接崩掉（−18.8 pp） |
| 原始 `ModernBERT-base`（MLM）当句向量 | **35.0 %**，比 8M 静态嵌入还差——训练目标压倒规模 |

唯一真正有效的是一个架构决定：把文本和选项**放在一起**打分（交叉编码），
而不是各自编码再比余弦。仅此一项就值 **+12 到 +24 pp**（依任务而定），
也正是一个 149M 的开源模型能落在 Jev 0.1 pp 以内的原因。

## 这份工作是怎么来的

**仓库作者不会编程。** 他贡献的是一个直觉和几次判断：

> *"最近很火的 Jev 模型，我感觉只是在一个决策模型前面加了一个快速处理文字理解的模型。
> 用静态嵌入、MiniLM、ModernBERT 做前置，能不能复现？"*

此后的每一个实验、每一次测量和全部分析，都由 **Claude Code（Opus 5）** 在一个工作
会话内设计并执行——包括八个失败的想法，以及它自己制造又自己发现的两个测量错误
（一次被并发 HTTP 流量污染的计时，一次被覆盖的结果文件）。

但这**不等于"AI 全自动完成"**。作者的三次介入改变了结果，而且没有一次需要写代码：

1. **"放弃 Qwen。"** 当时 agent 正在把一个生成模型集成进一个"全部用廉价本地零件"的
   方案里，而那个增益后来被证明是负的。
2. **"用完全公平的环境测试。我们自己要掌握真实数据然后再决定。"**
   这句话逼出了丰富描述的重跑——也产出了整个仓库里最有意思的发现。
3. **"你确定任务没有跑偏对吗？"** 确实跑偏了。这个问题把一天的工作拉回了原问题。

所有原始输出都已提交，所以这些数字是**可以核对的，而不是需要你相信的**。
我们认为基准测试就该这么发：不是"请相信我们的表格"，而是
"这是我们产生的每一个文件，请来挑错"。

## 接下来往哪走

零样本下的差距很小，延迟优势是真实的。两者都还没到头。
以下是我们**没有**试过的方向，大致按预期收益排序，欢迎 PR：

- **量化 / ONNX 导出**交叉编码器——预期同等准确率下延迟降到 1/3～1/5。
  这是目前最便宜的一笔收益。
- **更强的交叉编码骨干**：`deberta-v3-large-zeroshot`、`bge-reranker-v2`。
  我们 149M → 395M 的放大测试是净零，但那些是不同的模型家族。
- **混合候选裁剪**（BM25 + 向量）用于多选项任务。BANKING77 上我们的向量裁剪
  已经有 98.1% 的 recall@20，瓶颈在精排器而不在召回。
- **用比 1.5B 更强的模型做列表式精排**——我们试的 1.5B 失败了。
- **在多样化的分类数据上微调一个交叉编码器。** 这才是零样本下真正超过 Jev 的路，
  而它是一个训练项目，不是调提示词。
- **批处理 / GPU 服务**，这会彻底改变离线场景的成本格局。
- **更多数据集、更多语言。** 四个英文数据集只是很窄的一片。

## 局限

1. **Jev 的延迟几乎全是网络。** 从我们的位置看，2 个选项和 77 个选项都是约 381 ms
   （input token 差 5 倍，延迟差 5%）。它自身的计算时间小到我们测不出来。
   "本地快 7 倍"的意思是我们省掉了一次往返，不是算得更快。
2. **单随机种子、单机、每个配置只跑一次**，没有置信区间。
   子样本抽查显示结果会有 ±2 pp 的波动。
3. **校准（ECE）的对比不公平。** 我们的温度是在 1,000 条带标签 dev 上标定的，Jev 没有。
4. **我们不是 TypeSafe。** Jev 对我们是黑盒，只能从 API 观察。
